살펴봐야 할 KV Cache

head dimension과 KV head 수의 차이는 서빙 엔진의 KV 메모리에 어떤 영향을 줄까?

Taeyang Yun · LLM inference

Speculative decoding의 draft 모델을 설계할 때는 target 모델이 draft의 예상 토큰을 얼마나 많이 수용할 수 있을지를 먼저 고려한다. 하지만 draft 모델 아키텍처 관점에서는 draft와 target의 attention 구조가 다를 때, 추론 엔진이 KV cache를 어떻게 관리하는지도 중요하다.

같은 수의 토큰을 저장하더라도 head_dim과 num_key_value_heads가 다르면 KV page 크기가 달라진다.
이 글에서는 target 모델과 draft 모델의 head_dim과 num_key_value_heads를 다르게 설계한 사례를 살펴본다.

먼저 용어를 구분하자. 여기서 token block size는 한 block이 담는 토큰 수이고, physical page size는 해당 block을 저장하는 물리적 메모리의 바이트 크기다. 두 값을 모두 ‘block size’라고 부르면 서로 다른 문제를 혼동하기 쉽다.

KV Page 크기는 무엇으로 결정될까?

일반적인 attention에서 한 레이어가 토큰 하나의 Key와 Value를 저장하는 데 필요한 데이터 크기는 다음과 같다.

KV bytes / token / layer=2×NKV×Dhead×S

2는 Key와 Value, NKV는 KV head 수, Dhead는 head dimension, S는 원소 하나의 바이트 수다. 한 page가 B개의 토큰을 담는다면, 데이터 크기는 위 값에 B를 곱해 구할 수 있다.

이 식은 일반적인 K·V 저장 방식의 단순화된 계산이다. 실제 물리적 할당은 padding, alignment, quantization metadata, cache layout과 tensor parallelism에 따라 달라질 수 있다.

1. Head Dimension 차이

MiMo 2.5 Pro DFlash

vLLM PR #45181은 MiMo 2.5 Pro DFlash를 서빙할 때 발생하는 mixed KV page 문제를 다룬다. 이 사례에서 target의 head_dim은 192, draft는 128이다. KV head 수와 cache dtype이 같고 두 page가 같은 수의 토큰을 담는다고 보면, target과 draft의 page 데이터 크기는 3:2 비율이다.

Target pageDraft page=192128=32

두 모델의 physical page 크기를 하나의 단위로 관리하려면 이 차이를 조정해야 한다. page 크기가 정수배라면 작은 쪽의 token block 크기를 늘리는 방법을 쓸 수 있지만, 3:2 비율에는 그 방식을 그대로 적용할 수 없다.

PR은 작은 draft page에 padding을 더해 physical page stride를 맞추는 경로를 추가했다. 이때 논리적인 token block 크기는 유지하고, attention backend가 조정된 stride를 올바르게 해석하도록 reshape 처리를 포함했다.

결과적으로 Head Dimension 차이로 인해 draft page에는 KV 데이터가 채워지지 않는 padding 영역이 생긴다. 즉 head_dim 차이를 지원하기 위해 page stride를 맞출 수는 있지만, 그만큼 실제 KV를 저장하지 않는 물리적 공간을 추가로 할당하게 된다.

2. KV Head 수 차이

같은 토큰 수와 KV cache dtype을 사용하더라도, draft의 KV head가 더 많으면 draft attention의 KV page가 더 클 수 있다. Cache page의 크기를 통일하는 경로에서는 이 차이가 target의 token block 크기나 다른 cache의 padding에 영향을 줄 수 있다.

Nemotron 3.5 Super VL과 LiLiCorr

Nemotron 3.5 Super VL NVFP4 target과 LiLiCorr draft의 설정을 비교하면 KV head 수가 각각 2와 8이고, head dimension은 모두 128이다.

설정TargetLiLiCorr draft
num_key_value_heads28
head_dim128128

TP=1이고 두 모델이 같은 KV cache dtype을 사용한다면, draft의 attention 레이어당 토큰별 KV 데이터는 target의 4배다.

Draft KV bytes / token / layerTarget KV bytes / token / layer=8×1282×128=4

이 4배는 TP=1에서 attention 레이어 하나의 토큰별 KV 데이터 크기를 비교한 값이다. 전체 cache 사용량은 레이어 수와 cache 관리 방식에 따라 달라진다.

Target & Draft Page 크기 통일화

vLLM v0.32.0의 page 크기 통일 경로에서는 가장 큰 physical page를 기준으로 작은 page를 조정한다. 아래는 draft page가 더 크고 이 경로가 선택된다고 가정한 예시다. 같은 BF16 KV dtype에서 target의 token block을 늘리면 두 attention page를 64 KiB로 맞출 수 있다.

KV 메모리 점유와 Prefix Cache 재사용에 미치는 영향

Speculative decoding을 사용하지 않을 때와 비교해서 target의 token block이 커지면, 메모리 할당 단위가 커진다. 요청 길이가 큰 block 경계에 맞지 않으면 마지막 block의 빈 슬롯까지 예약하므로, 같은 요청 수에서도 target cache가 더 많은 메모리를 차지할 수 있다. Nemotron처럼 Mamba state와 attention을 함께 쓰는 하이브리드 모델에서는 page 통일화 과정에서 Mamba state page도 padding되어 물리적 할당량이 늘 수 있다. 또한 Draft의 KV cache까지 추가되면 전체 KV 메모리 점유와 cache 사용률이 더 높아질 수 있다.

vLLM의 prefix cache는 완성된 KV block 단위로 재사용한다. 따라서 token block이 커지면 공통 prefix가 더 큰 block 경계까지 일치해야 해 prefix cache hit가 될 수 있다. 더불어 Mamba state cache는 block 경계에서만 상태를 저장하므로, block이 커질수록 prefix를 재사용할 수 있는 간격이 더 커지게 된다.

Sliding Window는?

LiLiCorr는 다섯 draft attention 레이어에 8192-token sliding window를 사용한다. 이를 지원하는 cache 관리 경로에서는 window 밖의 KV block을 회수할 수 있지만, sliding window가 page 하나의 바이트 크기를 자동으로 줄여 주지는 않는다.

결론

Target과 draft의 head_dim과 num_key_value_heads가 다르면 추론 엔진에서 추가적인 구현이나 버그 수정이 필요할 수 있고, KV cache 관리 방식에 따라 메모리 비효율이 생길 수 있다. 따라서 draft 모델을 설계할 때부터 target의 attention 구조와 사용할 추론 엔진의 KV cache 관리 방식을 함께 고려하는 것이 중요하다.
